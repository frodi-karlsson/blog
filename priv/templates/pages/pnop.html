npm granular access tokens are capped at 90 days. There's no way to mint one that lasts longer, so installing private packages means rotating a token four times a year.

OIDC doesn't help here. It gives CI an identity a registry can trust, which covers publishing, but my laptop has no such identity to present. This discussion has people working through the same thing and arriving nowhere better.

Multiply that by everyone

On its own the rotation is a minor chore. You run an install, it fails on a 401, and you spend a few minutes generating a token and pasting it into ~/.npmrc.

In an organization it isn't one chore. The credential is shared, so someone rotates it and updates the vault, and then every developer still has to get the new token into their own ~/.npmrc, and nothing prompts them to. They find out when an install fails, which is to say at the least convenient moment available, four times a year, each of them separately.

So the token I needed was already in 1Password. The copy on disk had just gone stale.

pnop

pnop is a small Go binary that forwards everything to pnpm. If a command succeeds, it does nothing at all.

If a command fails, it reads what pnpm printed. Unless pnpm reported a registry authentication problem, pnop stays out of the way, so a failing test suite or a type error never reaches for the vault.

My first attempt decided this from the command instead, with a list of subcommands that never touch the registry. That can't work. pnpm runs any package.json script as a bare subcommand, so a script that shells out to a compiler and a real pnpm command that hits the registry are indistinguishable from the outside. Whether the registry was contacted is a fact about what the process did, not about how its arguments looked. Reading the output also catches a registry failure inside a script that happens to wrap pnpm, which no amount of inspecting arguments would find.

When pnpm did report an auth problem, pnop compares the token in your .npmrc against the one in 1Password:

  • They match. The token isn't the problem. The original error and pnpm's exit code pass through untouched.
  • They differ. Rewrite the .npmrc with the fresh token and rerun the command once.

That's the whole idea. The rerun is conditional on the token having actually changed, so a command that failed for any other reason never runs twice.

Two things I was careful about:

1Password is not touched on the happy path. The config isn't even loaded until a command has failed, and not even then unless pnpm said the registry turned it away.

pnpm's exit code survives. The wrapper returns whatever pnpm returned, so scripts and CI see the real number rather than pnop's opinion of it.

Setup

brew install --cask frodi-karlsson/tap/pnop

pnop setup -c work --vault=MyVault --item="My item" --field=MyField

The field's value can be a bare token or a whole //registry.npmjs.org/:_authToken=<token> line.

You can define more than one config and switch between them, which I use for work and personal registries:

pnop setup -c personal --vault=MyOtherVault --item="My other item" --field=MyField
pnop setup -c personal   # switch
pnop setup -c work       # switch back

Switching rewrites the npmrc with that config's token. Running setup -c against the config that's already active just refetches, which is the manual override when you want one.

Then in my shell config:

alias pnpm=pnop

What this doesn't solve

CI. The 90-day rotation still applies to whatever token your pipeline uses, and pnop has no answer for that. It's a local tool that happens to know where my token lives. The discussion above lists the actual options there: GitHub Packages with the built-in token, a registry proxy, or an automated rotation workflow. All of them are more work than an alias.

It also doesn't make the expiry go away. It moves the recovery from "notice, open a browser, generate, paste, rerun" to "the rerun already happened," which is as much as I wanted from it.
